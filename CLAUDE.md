# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Gridelle is a Tauri 2 desktop editor (React + TypeScript front end, Rust back end) for building modular synths on a grid and exporting them as Pure Data patch folders for the Critter & Guitari Organelle M.

## Commands

Prerequisites: Node 22+, stable Rust, and a C compiler (`build.rs` compiles libpd from source).

```sh
git submodule update --init --recursive   # vendored libpd; the Rust build asserts it is present
npm install

npm run tauri dev      # the desktop app, with audio preview
npm run dev            # UI only in a browser on :1420; editing works, the engine is a silent stub
npm run build          # tsc typecheck + vite build
npx tsc --noEmit       # typecheck only (there is no linter)

npm test               # vitest: compiler, Pd file builder, model ops, registry, preview sync
npm run test:pd        # cargo test in src-tauri: real Pd (libpd), headless; plays tests/golden, measures module DSP
```

Single tests:

```sh
npx vitest run src/core/compiler/compiler.test.ts -t "is deterministic"
cd src-tauri && cargo test --test compiled_patches
cd src-tauri && cargo test --test module_dsp -- --nocapture   # prints measured pitch, levels and filter responses
cd src-tauri && cargo test --test sample_dsp                  # the sample helpers and modules, on a sample whose contents say what was read
cd src-tauri && cargo test --test wavetable_dsp -- --nocapture   # the Wavetable oscillator: prints what is between the harmonics, note by note
cd src-tauri && cargo test --test arpeggiator -- --nocapture     # the Arpeggiator: the order of each mode, Hold, and its steps to the sample
cd src-tauri && cargo test --test module_cost -- --ignored --nocapture   # measures what every module costs in real Pd and writes src/core/modules/costs.json
cd src-tauri && cargo test --test voicing -- --nocapture         # mono note priority and legato, and a unison group's copies' places
cd src-tauri && cargo test --test engine_audio -- --ignored   # opt-in: plays through the real audio device at -40 dB; the only test of the audio callback, scopes included
cd src-tauri && ORGANELLE_ADDRESS=<ip> cargo test --test organelle_send -- --ignored --nocapture   # opt-in: writes the patch Gridelle_Test to a real Organelle and starts it
cd src-tauri && ORGANELLE_ADDRESS=<ip> ORGANELLE_PATCH=flavours cargo test --test organelle_send -- --ignored   # the same with another fixture, or the path of any patch folder
```

### Golden files tie the two test suites together

`tests/golden/<fixture>/` holds the compiled output of each document in `src/core/fixtures.ts`, as a complete Organelle patch folder. The vitest compiler test compares against it with `toMatchFileSnapshot`; the Rust `compiled_patches` test then opens each folder in libpd and checks that it is silent at rest, audible on a chord, silent after release (or, for the fixtures it lists as drones, that it sounds throughout), prints nothing to the Pd console, and (for `basic-synth`) that knob paging, soft takeover and screen text behave.

So after any change that alters compiler output or a `pd-lib/modules` abstraction:

1. `npx vitest run -u` to rewrite the golden files, and review the diff.
2. `npm run test:pd` to prove the new files actually work in Pd.

Without `-u`, `npm test` fails on a golden file that no longer matches instead of rewriting it, and running the Rust tests without regenerating tests the old patches.

A fixture's sounds are not text, so the compiler test writes `samples.json` beside the patch: `CompileResult.samples`, what each file of sound is made from. `compiled_patches` plays such a fixture from a temporary copy, where it makes the sounds with the same `samples::write_all` the editor exports with (paths in the list are from the top of the repo). That is how the megabytes of a wavetable stay out of git.

A new entry in `fixtures` gets its golden folder on the next `npm test`, and the Rust test picks up every folder that contains a `main.pd`. `basicSynth` is also the document the app opens with (`src/state/store.ts`).

## Architecture

### Pipeline

```
PatchDocument ──compile()──► { "main.pd", "voice.pd", "ge-*.pd" } ──► preview engine (libpd) or export folder
 (src/core/model)  (src/core/compiler + pd-lib/modules)
```

`src/core` is pure TypeScript with no React or Tauri imports, and `compile(doc, library)` is a pure function. Both the live preview and the export run the same compile and write the same files, so what is heard in the editor is what lands on the device.

### Document model (`src/core/model`)

`PatchDocument` holds modules placed on a grid, cables (output port → input port; every cable is an audio-rate signal and an input takes one cable), and knob pages (4 knobs per page; always 8 pages, see below). All edits go through the functions in `ops.ts`, which never mutate and return the *same object* when nothing changed. The editor store relies on that identity: `apply()` skips the undo step when `next === doc`, and unsaved-changes detection is `doc !== savedDoc`.

`ops.ts` keeps a document valid while it is edited (one cable per input, no feedback loops, no overlapping tiles). `analyze.ts` checks the cable and loop rules again and reports them as diagnostics, because `parseDocument` accepts any well-shaped file, including ones with unknown module types.

A module dragged from the browser onto a port of another module is cabled in by `ops.addModuleAtPort`. `planPortDrop` decides what that means and is also what the canvas previews, so the two cannot disagree. The new module uses its first input and first output. On a free port it lands beside the port, or as near as there is room. On a cabled port it goes in between (dropped on an output, in front of everything that output feeds); when the spot beside the port is taken it takes that place in the row and `makeRoom(…, "right")` moves the tiles there along. A module with no input or no output to go in between with is cabled to the port alone.

`ops.removeModules` is the reverse: a module taken out of a chain leaves the chain patched. What fed its first input now feeds whatever its first output fed, looking through a run of removed modules; cables on its other ports go with it. Tiles are not moved back.

Copy, cut, paste and duplicate (⌘C, ⌘X, ⌘V, ⌘D) are `ops.copyModules`, `ops.pasteModules` and `ops.duplicateModules`. A `Clip` is the copied modules as they were (settings, name, pre-cord switches) and the cables between them. Cables to modules left behind are not copied, and neither are Organelle knobs, since a knob holds one setting. A paste gives the modules new ids and keeps the places they had to each other; the group goes where its corner is nearest to the asked cell with room for every tile, so nothing is pushed aside. A duplicate asks for the cells right below the originals. A sample module's copy is on the same sample, so a copied Recorder is `two-recorders` until it is given another.

The patch's samples (`samples`, set with `ops.setSample`) are described under Samples below.

`DOCUMENT_VERSION` is 3: version 3 brought the voice area. `parseDocument` refuses older files (nobody else used the editor then); `presets::seed` writes an example preset again over its file of an older version.

**The voice area** (`PatchDocument.voiceArea`, a rectangle of cells, and `model/area.ts`) decides where a module runs: a module whose tile lies inside it is copied into every voice (`voice.pd`), one outside it runs once (`main.pd`). So a patch reads left to right as before the voices (an arpeggiator, an LFO they share), the voices, and after them (master effects, the output), though only inside or outside counts. Its outer ring of cells is its border (`AREA_BORDER`), where no tile goes, so that inside and outside never touch and are easy to tell apart; the top row of it is the header, which holds the number of voices and the voices' Notes input. The inside is `interior(area)`.

- `placement(doc, module)` is `inside` (within the interior), `outside` (clear of the area) or `across` (on its border). A tile is never across: `ops.canPlace`, `canMove`, `findFreeCell` and `pasteModules` refuse such cells, and cells inside for a module whose def says `place: "outside"` (Audio Out, Audio In, Recorder, Tape Head, Arpeggiator). `analyze` reports either as the `misplaced` error, since a file may hold them.
- To the tiles outside it the area is one big tile: `makeRoom` pushes it, with its tiles, and it pushes them. Inside, tiles push each other, and the area grows (right and down) to hold them, pushing what is outside along. A tile dropped into a row next to a port takes the side of the edge its neighbour is on (`addModuleAtPort` passes `inside` to `makeRoom`). `moveArea` moves it with its tiles, refused onto a tile outside; `resizeArea` pushes the tiles outside that the new edges reach along with the border, each the shortest of the ways the area grew and each pushing what it lands on; it is refused when a tile inside would come onto the border or out, or below `MIN_AREA` (the border round one cell).
- A cable crossing the edge outward is added up over the voices (an `outlet~` of `voice.pd`, which `[clone]` sums); inward, every voice gets the same signal (an `inlet~` of `voice.pd`: `[clone]` gives each copy the signal at its signal inlets, in Pd 0.49 too, and Pd computes the source first, so no block is lost). `analysis.outward` and `.inward` list them, one per output. Because Pd runs the area as one object, a way out of the area and back in is a feedback loop even when no module feeds itself: `connectionProblem` and `analyze` treat the area as one node for that.
- Which side a module is on is in `structureKey` (`placement` per module), so crossing the edge reloads and moving within a side does not.
- **Voice behaviour** (`PatchDocument.voicing`, `DEFAULT_VOICING` when absent; changed with `ops.setVoices` and `ops.setVoicing`). Poly plays `voices` notes at once, each on a voice of its own; Mono one at a time from the held keys, on one voice. The header shows the count (or Mono); a click on it shows the settings in the settings pane (`VoiceSettings` in `Inspector.tsx`). Unison is not a voice setting but a container of its own (below).
  - In `main.pd` poly is `[poly voices 1]` as before; mono is `ge-mono <priority> <legato>` then `list prepend 0`. `ge-mono` keeps each key's place in the order it came (0 for up) and its velocity in two tables, and at every key scores the 128 places: Last by that order, Lowest and Highest by 128 less the place counted from the bottom or the top. When the winner changes it sends `pitch velocity legato` (off when nothing is held), legato 1 when a note was sounding and Legato is on.
  - A voice's note is `pitch velocity legato`. `ge-voice` dips its gate for 1.5 ms at a note-on so that envelopes start again, except at a legato one, which only moves the pitch and velocity (a Glide then glides). Mode, priority and legato reload.
  - The `mono-lead` fixture is a mono legato patch whose saw is in a unison group of three, which `compiled_patches` plays: a second key held sounds alone, and letting it go returns to the first. The three detuned saws beat about once a second, and their fundamentals cancel at one point of each beat, so the test hears each note for a whole beat and takes its loudest moment.

**Unison groups** (`PatchDocument.groups`, `UnisonGroup`: an id from the modules' `ge<n>` ids, an area and a size). A group is a container like the voice area, one level down: what is in it runs `size` times side by side, added up where a cable leaves it, and every copy gets what a cable brings into it. So only what is put in it is copied: four voices with their saw in a group of five run twenty saws and four filters.

- **Containers** (`model/area.ts`): the patch (`MAIN`), the voice area (`VOICE`) and the groups. A group lies wholly inside the voice area or wholly outside it, never in another group; a module is in the innermost container whose inside holds its tile (`containerAt`, `containerOf`; `null` on a border). Modules that run once (`place: "outside"`) are in no container. A group has the voice area's border ring and header, and the same `MIN_AREA`.
- **Pd**: a group's modules are in a file of their own, `ge-unison-<id>.pd` (`groupFile`), run by `[clone ge-unison-<id> <size> <voice>]` in `voice.pd` (`$1`) or `main.pd` (-1); in a copy `$1` is its number and `$2` the voice's, which a Scope there takes. `analyze` gives every module its `container`, and lists each container's crossings: a cable crosses every edge on the way from its source up to the container both ends are in and down from there (`containerChain`), and `emit`'s `wiring` connects it in that innermost container, each container on the way passing it on at an `inlet~` or `outlet~`. A pre-cord in a group gets the voice's signal (`ge-voice`, or `ge-keyboard` for a group outside the voices) through the group's edge, as a crossing from `VOICE_SOURCE`. A way out of a group and back in is a loop to Pd, like one through the voices: `analyze` and `connectionProblem` treat each container as one node.
- **Shelves.** A container's shelf, the left column of its border below the header, holds outputs (`VOICE_SHELF`, `UNISON_SHELF` in the registry; `shelfPorts` in `model/area.ts`). A cable from one names the container as its module: `"voices"` (the pseudo module of the voices' Notes input) or the group's id. The voice area's give the voice's Pitch, Gate and Velocity, as a pre-cord would; a unison group's give each copy its place among the copies, Index from -1 (the first) to 1 (the last), evenly between, and 0–1. A shelf's output goes only to modules in its container, deeply (`connectionProblem`, `bad-cable` in `analyze`): outside it the signal would be added up over the voices or copies. `moveModules` and `moveContainer` drop such cables once their input has left (`dropStrandedShelfCables`); a copied group keeps its own.
  - In `analyze` a shelf cable is a `Wire` from `VOICE_SOURCE` (with the voice signal's `VOICE_OUTLET`) or from the group's id (the port's index); `sourceContainer` says where a wire's source is, so a voice-shelf cable into a group crosses its edge like a pre-cord there. `emit` takes a group's from `ge-unison-place $1 <size>` in its file, which computes `(k - h) / h` with `h = (size - 1) / 2`, and `(place + 1) / 2` at its second outlet. Into an oscillator's Fine tune input, Index spreads the copies over plus and minus the knob's cents.
  - The shelf's ports are drawn at the right edge of its column, two to a cell (`shelfPortPoint` in `VoiceArea.tsx`), and take cables like any output.
- **Editing** (`model/layout.ts`, `Boxes`): the tiles, the groups and the voice area are boxes in boxes. A box pushes only those in the same container; a container grows (right and down) to hold what was pushed in it and then pushes what is beside it, so a group in the voices that grows makes the voice area grow. `makeRoom`, `moveContainer`, `resizeContainer` (with `moveArea`/`resizeArea` for the voice area) and `moveModules` all work on it; `layoutAllowed` is what they must leave. A container grows on whichever side something lies past its inside (`Boxes.fit`). `moveModules` keeps a module in its container, or lets it go into one in it: dragged past the edge, the container grows with it and pushes what is beside it, which can push the border of the next container in turn. With `leave` (Shift held while dragging) it goes wherever it is dropped, out of containers too, and is refused across an edge. `addGroup` puts down an empty group (`NEW_GROUP`, 4 by 5, room for an oscillator; the tests use it, the editor does not) and `setGroupSize` sets its copies. `wrapInGroup` (⌘G, or Edit > Put in Unison Group) puts the selected modules in a new group, its border a cell round them; what else lies on its cells, between them too, is pushed out the shortest way (right, then down, on a tie) and pushes on, and the voice area grows if the group reaches past its border. `wrapProblem` says why a selection cannot be wrapped: modules in different containers, in a group already, or one that runs once. `ungroup` (⇧⌘G, Edit > Ungroup) is the way back: the selected groups go, and what was in them stays where it is, in the container the group was in, selected; the cables from a group's shelf go with it. A selected group is deleted, copied and pasted with what is in it (`removeModules`, `copyModules`/`pasteModules`, whose `Clip` has `groups`); the marquee selects a group it covers whole.
- **The editor**: a group is made round the selected modules (⌘G, or Edit > Put in Unison Group); the module browser has no card for one, and the settings pane no button. A group is drawn like the voice area, tinted (`.container-unison`), with Unison − N + in its header; a click on the header selects it, and the settings pane shows its copies and what they do (`GroupInspector`).
  - A Scope in the voices shows the first voice of the latest note (voice 0 in mono). `src-tauri/tests/voicing.rs` plays the three helpers; the `mono-lead` fixture is a mono legato patch, which `compiled_patches` plays: a second key held sounds alone, and letting it go returns to the first.
- Outside the area a pre-cord follows the keyboard as one part (`ge-keyboard`, from `r notes`: the last key's pitch and velocity, and a gate on while any key is held, which does not dip when another key goes down), and Keys there is the keyboard. Inside, both follow the voice's note (`ge-voice`), as before. The editor says which (`precordText`).

A new document field touches `types.ts`, the hand-written shape check in `serialize.ts` (plus `DOCUMENT_VERSION` if older builds cannot read the result), and `structureKey` if it changes the emitted patch.

A module can have a name of its own (`ModuleInstance.name`, set with `ops.renameModule` from the field at the top of the settings pane). `ops.moduleName` is what a module is called: that name, or its type's when it has none. It is what the tile shows, what names the module's settings in the Knob pages panel and on the Organelle's screen (`slotLabel`), and what diagnostics call it. The name is in `structureKey` only for a module with a setting on a knob, since nothing else of it is exported.

Module ids are `ge<n>` and must match `/^ge[0-9a-z]+$/`. The id is also the module's Pd creation argument and the prefix of its parameter receivers (`ge3-cutoff`); the `ge` prefix keeps them clear of the names the Organelle host uses (`knob1`, `notes`, `aux`, `vol`, …). Generated plumbing uses names with a hyphen straight after `ge` (`ge-page`, `ge-slot-<page>-<knob>` with a 0-based page and 1-based knob, the `ge-*` abstractions), which no module id can produce.

### Modules: a registry entry plus a hand-written Pd abstraction

A module is two things that must agree:

- a `ModuleDef` in `src/core/modules/registry.ts` (ports, params, tile size, scope);
- `pd-lib/modules/<def.pd>.pd`, a flat abstraction whose `inlet~`/`outlet~` objects match the def's inputs/outputs left to right, and which has one `[r $1-<paramId>]` per param. No control inlets or outlets.

`registry.test.ts` enforces the match by parsing the `.pd` text (`src/core/pd/inspect.ts`, flat patches only, no subpatches). It also checks that every object class used is one the device has: the allowlist of Pd 0.49's core in `src/core/pd/vanilla049.ts`, or `PD_EXTRA_049` there, the few objects from Pd's `extra` folder that modules wrap (see below). The preview embeds a newer Pd than the device has, so an object missing from those lists could work in the editor and fail on the Organelle; extend them only after checking the object exists in Pd 0.49.

Labels are whole words (Resonance, Modulation, Attack): they name the rows of a tile and are read in the settings pane's texts. `ParamDef.short` is the name for the Organelle's screen where the label does not fit on a line with the module's name and the value (`Low-pass Res 0.5`); `slotLabel` in `knobPages.ts` tries the label, then the short name, then trims the module's name. Ids keep their old short forms (`res`, `mod`, `depth`, `cv`), since saved patches and the abstractions' receivers use them.

Params are stored and sent in real units (Hz, ms, semitones). `ParamDef.decimals` fixes how many decimals a value is shown with, in the editor and on the Organelle's screen, where the default (fewer for a wider range) would hide the low end, as with an LFO's 0.02 Hz. `params.ts` maps a 0–1 control position to a value (`lin`/`exp`); `knobPages.ts` emits the same mapping as Pd objects, so the two must stay equivalent.

A param with `options` is a choice (an oscillator's Modulation mode). Its value is the option's index, so it is stored, clamped and sent like any other number, and changing it is a live update, not a reload. The inspector draws it as a list; it gets no knob on the tile, and so cannot be put on an Organelle knob, whose screen line would show the bare index.

A param with `entry` is a number typed in the settings pane (`EntryRow` in `Inspector.tsx`, set as it is typed once it is a number), with no knob on the tile and no input of its own; the tile shows the value instead of its picture (`.tile-value`). The Constant is the one: a one-cell tile that gives its Value, from -10000 to 10000, through a 20 ms ramp.

**Helper abstractions.** `pd-lib/modules` also holds abstractions that are not modules (`ge-voice`, `ge-keyboard`, `ge-mono`, `ge-unison-place`, `ge-knob`, `ge-blep`, `ge-osc-mod`, `ge-filter-poles`, `ge-drive`, `ge-seq-step`, `ge-peak`). `compile()` ships a module's file together with everything it is built from, transitively (`withHelpers` in `compiler/index.ts`): any object class in an abstraction that is not on the Pd 0.49 allowlist is taken to be another abstraction, and is a `missing-abstraction` error if the library lacks it. Parameter receivers (`[r $1-<id>]`) must stay in the module's own file, because that is where the registry test looks for them.

**Measured, not assumed.** `src-tauri/tests/module_dsp.rs` loads each abstraction in real Pd and checks what it does: oscillator pitch, level, DC and aliasing, and each modulation mode (including the side bands of linear FM); each filter's gain at several frequencies against the response it is designed to have; each shaper's output against its curve, sample by sample; the mixer's sum; the envelope's stages with each input at several values; the compressor's curve and timing and the limiter's ceiling; the clock's ticks and the sequencer's steps; and for every setting input, that the knob at `v` with the input at `k` gives the same samples as the knob at `v * k`. Change the DSP of a module and this is the test to extend. (It found that the first Low-pass, built on `vcf~`, went silent when opened fully.)

**Oscillator modulation.** Every oscillator ends its pitch chain (note + Tune + Fine tune) in `ge-osc-mod`, which takes the Modulation input, its knob (`depth`) and Modulation mode and returns the frequency in Hz and an output gain. That frequency is an octave below the note (`-~ 12` before `mtof~`): at Tune 0 middle C on the keys plays C3, 130.8 Hz. The sample modules are not shifted: middle C still plays a sample at its own speed. Only the selected mode's amount is non-zero, each behind a 20 ms ramp: linear FM is `frequency * (1 + mod * 8 * depth²)`, exponential FM adds `mod * 48 * depth²` semitones before `mtof~`, AM is a gain of `1 + mod * depth`. The mode numbers in the registry's option list must match the `[== n]` objects there. Linear FM can take the frequency below zero, where `phasor~` and `osc~` run backwards; `ge-blep` therefore takes the absolute frequency.

**Filters** are the standard "cookbook" (RBJ) biquads, built so the cutoff can move at audio rate: `ge-filter-poles` makes the pole pair from two `cpole~` with signal-rate coefficients and outputs the gain each filter type needs; the module adds its zeros with `rzero~` (Notch is the input minus the band-pass). Coefficients come from the sine and cosine of *half* the angle, because Pd's cosine table is too coarse to take `1 - cos w` from near zero. Resonance (times its input, clipped to 0–1) maps to Q 0.7–15, and Low-pass and High-pass are turned down by `sqrt(0.7/Q)`.

**Shapers** have an In and a Modulation input, besides the inputs of their settings. Soft Clip, Hard Clip and Wavefolder share `ge-drive`: Drive in dB before the shaping, plus Modulation dB per unit of the mod signal.

- Soft Clip is `tanh` written with `exp~`, with a Bias that shifts the signal first.
- Wavefolder reads a triangle with the signal (`wrap~`, `abs~`) or, with Shape set to Sine, a sine (`cos~`); Symmetry is its shift.
- Rectifier multiplies the negative half by `1 - 2 * amount` (0 clean, 0.5 half-wave, 1 full-wave).
- Bitcrusher holds samples with `samphold~` clocked by a `phasor~` at Rate, then rounds to `2^(bits - 1)` steps per side (`x + 0.5` minus its `wrap~`).
- Chebyshev builds T1–T8 with the recurrence `T(n+1) = 2x T(n) - T(n-1)` on an input clipped to ±1; Harmonic (`order`, moved by Modulation) fades between neighbouring polynomials.

A shaper must give exactly 0 for silence, or every voice whose amp is closed puts DC or a thump into whatever comes after it. So whatever a shift (Bias, Symmetry) alone would produce is subtracted after the curve, and the even polynomials are moved to be 0 at 0. The `hip~ 5` that ends the lopsided ones only removes the DC that appears while a signal is present; the DSP test runs the same filter over its expected curve. None of the shapers is oversampled, so hard driving aliases.

A bare `;` in a Pd comment ends the box, and Pd then tries to deliver the rest as a message on load ("no such object"). `registry.test.ts` checks every abstraction for it.

**Setting inputs (Eurorack style).** Every setting with a knob has an input of its own: `PortDef.param` ties an input to a parameter, and the module multiplies the two, so the knob scales what is patched in. `PortDef.unpatched` is the signal such an input holds with no cable (1, so that the knob alone gives the value). A Pd abstraction cannot tell whether an `inlet~` is connected, so the compiler supplies it: `analyze` lists the unpatched inputs as `constants`, and `emit` adds one `[sig~ <value>]` per value to `voice.pd` or `main.pd` and connects it. A test patch has to do the same (`with_module` in `module_dsp.rs`), or the setting is multiplied by 0.

- The multiplication is at signal rate, on the smoothed knob value, in the unit the knob shows: a filter's Cutoff input multiplies Hz (after Modulation has been added in semitones), a shaper's Drive input multiplies dB.
- A **Modulation** input (port id `mod`) is tied to its amount knob (`depth` on the oscillators, `mod` elsewhere, both labelled Modulation) and has no `unpatched`: it rests at 0 and adds to another setting, as before. The Pulse's Width modulation (`pwm`) has no knob. The Amp's Level input has the id `cv`.
- Choices have no input.
- The ADSR is the exception to "signal rate": it reads its inputs when a stage starts. `snapshot~` takes Attack, Decay and Sustain at gate on and Release at gate off, times the knob values, into the one `vline~` it always had (which is what keeps a retrigger from clicking). A change during a stage waits for the next one, and a negative product counts as 0.
- The AR and the AD are built the same way, with the same exception. AR is the ADSR without its middle: `1 <attack>` into `vline~` at gate on, `0 <release>` at gate off. AD sends the whole shape at the rise of Trigger (`1 <attack>, 0 <decay> <attack>`), so the gate's length does not matter. With Loop on, a `delay` of attack + decay fires it again through two `spigot`s, one open while Trigger is on and one while Loop is; the delay is never under 1.5 ms, or a cycle of no length would fire for ever within one moment of Pd's time. Shape set to Curved gives the square of the envelope (`x + c(x² - x)`, with `c` the choice behind a ramp). The option orders in the registry are the numbers those receivers get.
- A filter's Resonance goes through `exp~` to become Q, so Q and the level trim are signals, and `ge-filter-poles` takes Q at a signal inlet. `ge-drive` has a signal inlet that multiplies Drive.

**LFOs.** `ge-lfo` and `ge-lfo-random` are modulation sources with two outlets: the wave between -1 and 1, and the same wave between 0 and 1 for the inputs that multiply a setting. Level scales both.

- The LFO computes its five shapes from one `phasor~` and multiplies each by a 0/1 gate from the Shape choice (the option order in the registry must match the `[== n]` objects). Sine and Triangle are shifted to start at 0 going up. Reset sets the phase to 0 on a rising edge, and has the gate pre-cord, so by default each note's LFO starts from the beginning; with the pre-cord off it runs free.
- Random clocks a `samphold~` of `noise~` with a `phasor~`. A second `samphold~` behind a one-sample delay (`biquad~ 0 0 0 1 0`) keeps the previous value, and Smooth is the part of each tick spent gliding between the two. Every `noise~` has its own sequence, so each voice gets its own values.

**Effects** (`ge-fx-*`) are modules like any other: in the voice area each voice has its own, outside it they run once. Their tails ring out by themselves: nothing cuts a voice off.

- Delay lines are named with `$0`, which differs in every copy of an abstraction, so each voice has its own. Never name one with `$1`: that is the module id, the same in every voice.
- A delay line that feeds itself cannot be shorter than one block (64 samples, 1.5 ms): the Delay's shortest time, the Chorus's 2 ms base and the Reverb's shortest all-pass (1.7 ms) are all above it. The Phaser needs its feedback sooner than that, so it runs at `block~ 16`.
- Delay: `vd~`, fed back through a one-pole low-pass (`rpole~` with a signal coefficient) at Tone. Chorus: two `vd~` taps swept a quarter cycle apart by its own LFO, the left one fed back. Phaser: four first-order all-pass stages (`rzero_rev~` then `rpole~` with the same coefficient), swept in pitch around 784 Hz. Reverb: four fed-back delays in parallel, each with the gain that makes it fall 60 dB in Decay seconds and a low-pass at Damp, summed differently for left and right, then two Schroeder all-pass delays a side.
- All-pass (in the Filter group) is the input minus twice the band-pass, from the same `ge-filter-poles`.

**Wrappers of Pd's own objects.** Some modules are a thin patch around an object of Pd itself, for another flavour of a job Gridelle already does: Ladder (`bob~`), Resonator (`vcf~`), Soft Low-pass and Soft High-pass (`lop~`, `hip~`), Cavern, Room and Hall (`rev1~`, `rev2~`, `rev3~`), Sample & Hold (`samphold~`) and Follower (`env~`).

- `bob~` and the three reverbs live in Pd's `extra` folder. An exported patch names them and does not carry them: the Organelle's Pd has them (checked on a device with OS 3.2, where they are in `/usr/lib/puredata/extra`). The preview's Pd gets them in `Pd::init()` (`engine/pd.rs`): `bob~` is compiled in and set up there, and the reverbs' five `.pd` files are embedded from the vendored Pd, written to a temp folder and put on the search path. A new one needs `PD_EXTRA_049`, and `EXTRA_SOURCES` in `build.rs` or `EXTRA_ABSTRACTIONS` in `pd.rs`.
- `Pd::init()` also sends `pd compatibility 0.49`, so the preview behaves as the device's Pd where Pd offers the choice. Of the things that make sound that is `bob~`, which before 0.52 gave the first of its four stages: on the Organelle the Ladder falls 6 dB an octave, not 24. The DSP test measures exactly that, and a self-test patch run on the device gave the same numbers as the preview to four decimals (a sine three octaves above the cutoff comes out 17.66 dB down).
- Where Pd wants a setting as a number (the Resonator's Q, the reverbs' decay, damping and crossover, the Follower's Smooth), the knob times its input is read with `snapshot~` on a 10 ms `metro` and sent on when it has changed. Those inputs work, but not per sample.
- The soft filters are not the objects themselves: `lop~` and `hip~` take their cutoff as a number in Pd 0.49. They are rebuilt from `rpole~` and `rzero~` with the same coefficients, and the DSP test compares them with the real objects.
- Decay is in seconds on all reverbs. For Room and Hall it becomes a liveness percentage through a loop time measured in the DSP test. For the Cavern, `rev1~`'s help is wrong about its own setting: measured, it takes 216 / (100 - dB) seconds to fall 60 dB and never under 2.2 s, so that is the formula used and the range offered.

**Pitch modules** take and give a pitch the way the oscillators' Pitch input takes it: a note number as a signal (60 is middle C). Their Pitch input has the pitch pre-cord.

- Transpose adds 12 times Octave, Semitones and Modulation times its amount. Glide is a one-pole low-pass on the pitch, with the pole that covers 95 % of the way in Time. Quantizer adds Modulation times Range, splits the result into whole octaves above Root and a rest, and looks the rest up in a 13-entry table (`[table $0-scale]`, filled by the Scale choice) that maps each semitone to the nearest note of the scale, the lower one on a tie. The Scale options in the registry are in the order of `SCALES` in the generator.
- Keys (in the In / Out group) gives the played note as outputs: pitch, gate, velocity, and the pitch as 0..1 (outside the voice area, the keyboard's). It has no inputs: `voiceInlets` on its def names the voice signals its abstraction takes at its first inlets, and `analyze` feeds them through the same list as the pre-cords. A module's own inputs come after those inlets (`inletOf`).
- A voice's pitch is 60 until its first note, not 0 (`ge-voice`): an oscillator with nothing after it then sounds C3 (an octave down, as oscillators play), not a 4 Hz tick, and a Glide starts its first note from there.
- `ge-voice` and `ge-keyboard` make pitch and velocity with `vline~` jumps, not `sig~`: they change at the logical time of the note, to the sample, which is what an arpeggiator's notes have. `module_dsp.rs` checks both.

**Math and logic modules** work on any signal. Those without knobs (Add, Multiply, Min, Max, Abs, And, Or, Not, Toggle) are one-cell tiles in the plain layout; those with knobs use rows.

- Logic treats a signal as on above 0.5 and gives exactly 0 or 1. With no comparison objects on the Pd 0.49 list, a gate is a steep ramp through the threshold, clipped: `(x - 0.5) * 1000000`, `clip~ 0 1`.
- Toggle and Divider count rising edges as a signal: the gate through `rzero~ 1` and `max~ 0` is 1 at the sample it rises, and `rpole~ 1` adds those up. Toggle is whether the count is odd; Divider passes the gate while `(count - 1) / N` is a whole number.
- Smooth runs two one-pole low-passes, one at Rise and one at Fall, and takes the higher of them when Rise is the shorter time and the lower when Fall is. That is exact for a step, which is what it is for.

**Compressor and Limiter** (in the Level & Mix group) both turn a signal down by a level they measure, and both measure it with the helper `ge-peak`: the higher of the level now and the peak so far times a factor, which is a peak that is reached at once and let go slowly.

- That needs its own output of one sample ago, and Pd 0.49 has no object for it (`slop~` came in 0.50). So `ge-peak` runs at `block~ 1`, where a `delread~` of a `delwrite~` is one sample late. It has four objects to run for every sample; everything else in the two modules runs at the usual block. The level going in is kept above 1e-15, so that a peak dying away after a sound never becomes a denormal number.
- Times are the time to go 95 % of the way, as in Glide and Smooth: the factor is `exp(-3000 / (rate x ms))`.
- Compressor: the Sidechain's `abs~` through `ge-peak` (Release), then a one-pole low-pass (Attack), then `rmstodb~`. What that is over Threshold, times `1 - 1 / Ratio`, is taken off Gain, and `dbtorms~` of the result multiplies In. Under Threshold with no Gain the factor is exactly 1. Sidechain is normalled from In (`normalled`, as Audio Out's right side is), so a test patch has to feed it.
- Limiter: both sides times Gain, the higher `abs~` of the two through `ge-peak`, and both multiplied by Ceiling over the peak, where the peak counts as the Ceiling at least. The peak is never under the signal, so the output is never over the Ceiling, from the first sample; the DSP test checks that with a full-level sine that starts all at once. There is no look-ahead: a peak that comes before the gain is down is flattened at the Ceiling. Right is normalled from Left.
- The `dynamics` fixture has both outside the voice area, with Audio Out at full level, and `compiled_patches` checks that a chord peaks at the Limiter's Ceiling.

**Clock and Sequencer** (the Sequence group) are modules like any other: in the voice area each voice has its own, and by default each key starts its own; outside it one runs for all, its Run following the keyboard.

**Notes and the Arpeggiator.** Besides signals, a cable can carry notes: `pitch velocity` messages, from a port with `kind: "notes"` (hint `notes`: a pale cable and a square port) to another. In Pd a note port is a control `inlet` or `outlet`; `registry.test.ts` checks every abstraction's inlets and outlets, control and signal, in the order of the def's ports (`abstractionInterface().inlets`, by x). Only modules outside the voice area have note ports.

- The voices' Notes input (`VOICE_NOTES`, the pseudo-module `voices`, on the left of the area's header) is what `[poly]` is given: the keyboard's notes, or a note output cabled in (`analysis.voiceNotes`). A note input of a module with no cable gets the keyboard's too (`analysis.keyboardNotes`, from the `[r notes]` in `main.pd`). Notes never cross the area's edge as cables, and take no part in the loop through the voices: they are messages.
- The **Arpeggiator** (`ge-arpeggiator`, built by a script and as long as it is) keeps the held keys in two tables: a flag for each of the 128, and the order they were pressed in. Each step is one trigger, right to left: the sounding note off, the period, the numbers (keys held L, octaves, total = L x octaves, step k), the place j by Mode (up: k mod total; down: total - 1 - that; up and down: t = k mod max(1, 2 total - 2), then t or 2 total - 2 - t; as played; random), the note (the (j mod L)-th key, counted up from the bottom through the flags or from the order pressed, plus 12 x (j div L)), the next k, and the note's end after Length of the period. Hold keeps the keys after they are let go, until one goes down with none down.
- It steps on its own `metro` at Tempo in Division (a message-time clock, so the steps are exact to the sample, after the first, which comes with the keys). Its Clock input takes a Clock's Phase: `unpatched: -1` tells it nothing is there. Following a Clock it does not wait for the wrap to show (that would be up to a block late): once a block it reads the phase and how far it went, works out when it will go round, and when that is within the next block, sets a `delay` for that moment. `arpeggiator.rs` measures its steps within a sample of the Clock's ticks.
- The first step waits for the end of the moment the first key came (`delay 0`), so that a chord sent at once starts as a chord. Before a note-on it sends the sounding note's note-off, so it plays on one voice too.
- The `arpeggio` fixture is an Arpeggiator into the voices' Notes input; `compiled_patches` holds a chord and listens for each step's note in turn.

- Clock is a `phasor~` at Tempo / 60 times the ticks to a beat of its Division (a choice, so a `sel` and nine message boxes set the factor of a `*~`; their order is `CLOCK_DIVISIONS` in the registry). Out is on while the phase is below Width, and Phase is the phase itself. Run is a gate with the gate pre-cord and `unpatched: 1`: the clock runs while a key is held, or all the time with the pre-cord off. Both outputs are multiplied by Run. When Run comes on, `samphold~` takes note of the phasor, and the phase counts from there, so a tick starts at that very sample. Free clocks in different voices stay in step, since they all start with the patch.
- Sequencer counts the rises of Clock as a signal, as the Divider does (`rzero~ 1`, `max~ 0`, `rpole~ 1`). The count when a reset ended is kept by a `samphold~` and taken away, and what is left, modulo Steps, is the step being played, a whole number from 0. Each step is a copy of the helper `ge-seq-step`, which gives its knob times its input while the number is its own (`max~ 0` of 1 less the distance) and 0 otherwise; the eight are added up. Out is that sum, in semitones, plus Pitch; Value is the sum over 24.
- For 3 ms from a rise of Reset, and from the moment the patch loads (`loadbang` into `vline~`), the Sequencer is held on its first step and the clock rises in that time are not counted. Without it the first step would be skipped: a clock started by the same gate goes on at that sample, or a block later if it is an LFO, whose reset is a message. The DSP test runs a Clock into a Sequencer, free and on a gate, and checks that every step lasts from one tick to the next.
- The count is exact up to 2^24 ticks, and its division by Steps to about half of that: days at the fastest tick.
- A step's knob is in whole semitones (`step: 1`), but its input multiplies it to anything. The steps have `short` names of just their number, so that `Sequencer 1 -24 st` fits the Organelle's screen.
- The `sequence` fixture is a Clock into a Sequencer and an envelope; `compiled_patches` holds a key and listens for each step's note in turn.

**Samples.** A patch has up to eight samples (`PatchDocument.samples`, letters A–H in the editor, slots 0–7 in the patch), each a sound file or a blank tape of some seconds. A cable is a signal and cannot carry a sample, so the sample modules each choose one, and that shared choice is what links them: no cable is needed between a module that writes a sample and one that reads it.

- The choice is `sampleChoice`, a param with `argument: true`: the value is a creation argument of the abstraction (`$2`), has no receiver, is left out of `paramValues`, and is part of `structureKey`, so changing it reloads. Names inside a sample module are therefore fixed when it is created (`tabread4~ ge-sample-$2`). `argumentValues` in `analyze.ts` gives them in order; a `tap`'s numbers come after.
- `main.pd` gets one helper per slot a module uses (`analysis.samples`): `ge-sample-file <slot> <file>` reads `ge-sample-<letter>.wav` with `soundfiler` on load, `ge-sample-tape <slot> <seconds>` resizes its table to that many seconds at Pd's rate in whole blocks. An empty slot that a module uses is a tape of 0 seconds (one block of silence) and the `empty-sample` warning, so that Pd has a table and prints nothing. Both then send the rate in Hz to `ge-sample-<slot>-rate` and the size in samples to `ge-sample-<slot>-size`, in that order, which is what the modules compute from.
- `compile` stays pure: it names the sound files (`CompileResult.samples`, the name in the folder and what it is made from) and whoever writes the folder adds them. `src-tauri/src/samples.rs` decodes WAV, AIFF, FLAC, MP3 and Ogg Vorbis (the `symphonia` crate), mixes to one channel and writes a 16-bit WAV at the file's own rate, the one thing Pd 0.49's `soundfiler` reads without surprises (it takes a 32-bit WAV for float, refuses 8-bit and AIFC). Conversions are kept per path and modified time, since the preview reloads at every structural edit. `engine_load`, `export_patch` and `organelle_send` all convert first and fail with the file's name before touching anything.
- A sample module plays a sound at its own speed whatever rate Pd runs at, from the rate the helper sends. Positions on cables are 0–1 across the sample; that is a 32-bit signal, so beyond about 20 s a sample grows grainy at other speeds than its own (`long-sample` warning).
- **Sample Player**: a `phasor~` runs at one pass of the window (Start, Length) per cycle. A trigger takes note of the phase with `samphold~` (controlled by the gate upside down, since `samphold~` samples when its control falls), and the phase since then is the place in the window. The phase stepping back ends a pass; passes are counted (`rpole~ 1`) and the count at the trigger taken note of the same way. Middle C is the sample's own speed. Once plays to the end after the key is up, and its Playing output says for how long. Its Pitch input has both a pre-cord and `unpatched: 60`: `analyze` feeds one or the other.
- **Play Head** is `tabread4~` at Start + Position, wrapped.
- **Recorder** (outside the voice area, `sample: "writes"`, one per sample or `two-recorders`). Pd 0.49 has nothing that writes at a place a signal gives, only `tabwrite~`, which writes from the start to the end and stops. So the tape always runs: a count of blocks (`bang~`) re-bangs `tabwrite~` every lap, laps are whole blocks (`floor(size / 64)`), and what is written is `in × recording + old × kept`, where `old` is `tabread~` at the same place (read before it is written, since it feeds the writer) and `kept` is 1 while not recording, an exact rewrite, and Overdub while recording. Recording is the Record knob times its input, as a gate, through `lop~ 200`: a punch-in is sample-accurate and faded, and nothing is ever started or stopped. The place is the block count × 64 plus a 64-sample `phasor~` ramp that is put back in step each lap, read at + 0.5 because `tabread~` cuts fractions off. Out is `old`, so the Recorder alone is a looper. Once: a rise of Record sets a flag that the next block tick turns into a new lap (acting on the rise directly could land either side of that tick and leave the count a block out), and only that lap records.
- **Tape Head** (outside the voice area, `sample: "follows"`, `no-recorder` warning without a Recorder on its sample) plays what was written Delay ago. No cable joins it to the Recorder, so patching its output back into the Recorder is not a loop to `ops`, `analyze` or Pd: the tape is the delay. It learns where the recording is from `r~ ge-sample-<slot>-at`: the Recorder `throw~`s its place in samples, and the slot helper `catch~`es it and sends it on, so the receive always has a sender. That hop costs 0, 1 or 2 blocks, fixed for a patch, which adds to Delay. The delay in samples is split with `wrap~` into a whole number and a fraction, and two `tabread~` at whole indexes are blended: exact for any length of tape (a whole number survives a 32-bit signal, a position 0–1 does not), and with no seam where the tape goes round. Delay is kept between a block, behind which the recording is sure to have been written whatever order Pd sorts the two modules in, and the tape less four blocks.
- **Grains** (per voice, stereo) is four copies of the helper `ge-grain`, a quarter cycle apart on one `phasor~` at Density / 4, so a stream makes a grain every 4 / Density seconds and a grain lasts at most that long: four overlap. Each time a stream's phase starts again, `samphold~` (controlled by the phase itself, which falls there) holds what that grain is to be: its start (Position plus the stream's own `noise~` times half of Scatter, or that far back from `ge-sample-<slot>-at` when Position is counted from the recording), how far it reads in a cycle (the speed, as on the Sample Player), how much of the cycle it lasts, and where it is panned (other noise times Width, equal power). A change during a grain waits for the next, so a grain never jumps. The shape is a raised cosine from `cos~`; four full ones add up to 2, hence the 0.5 at the end. Overlapping grains from one fixed place add up or cancel as the pitch moves: that is the sound of it, and why the DSP test measures pitch on grains laid end to end.
- The `looper` and `tape-echo` fixtures are those two patches. `looper` is the one fixture that is meant to keep sounding with no key held, and `compiled_patches` checks that instead of silence.
- The Samples pane (`ui/samples/SamplesPane.tsx`, `state/sounds.ts`) is where samples are made and deleted. It is a side pane (below), opened from its tab. It lists the slots that hold something, a sound file by its waveform and a tape by a picture of reels with its length to set, and after them the next free slot with its two buttons, until all eight are in use. A sound's picture is read by the `sample_info` command and kept in `useSounds`, not in the patch. A sample module's Sample choice in the settings pane offers the samples the patch has, plus the one the module is on if that is empty.
- `tests/golden/sampler/ge-sample-a.wav` is committed by hand: it is the sound file the `sampler` and `grains` fixtures name.

**Wavetables.** The Wavetable oscillator plays one cycle out of a row of them (the frames of a wavetable) and fades to the next. A wavetable is a sample slot's: `{ kind: "wavetable", bank }` is one of the editor's own, and a sound file in a slot is read as one too, cut into cycles.

- **Why a table is more than its cycles.** A cycle read at a high pitch puts its upper harmonics past half the sample rate, where they fold back. So the editor stores each frame ten times, a level for each octave of pitch, level L with `512 >> L` harmonics, and the oscillator reads the level its pitch has room for. A level is used up to a quarter tone under an A (`floor((note - 20.5) / 12)`), so no tuned note sits where two levels meet; what folds back is then above 16 kHz at 44.1 kHz. The low levels are longer (4096 points) than the high ones (64), so that `tabread4~` has points enough between their many harmonics.
- **The file** (`src-tauri/src/wavetable.rs`) is one record of 16,414 points per frame: the frame's ten levels in a row, each a cycle with three guard points (its last point in front, its first two behind, which is what `tabread4~` reads around a place). One gain for the whole table brings its highest point to 1. At most 64 frames. It is a 16-bit mono WAV named `ge-wave-<letter>.wav`, about 2 MB for 64 frames, loaded by the helper `ge-wave-file <slot> <file>` into `table ge-wave-<slot>`, which sends `ge-wave-<slot>-size`.
- **Reading it exactly.** A 32-bit signal cannot say where in a million points to read to a fraction of a point. `tabread4~` has an onset that is a number, not a signal, and adds it in double precision. So `ge-osc-wavetable` works out where the frame and level in use start (`frame x 16414 + offset[level]`, an exact whole number), takes note of that once a block (`bang~` into `snapshot~`), and sends it to both readers' onsets and to a `sig~`. The index signal is `phase x length + 1` plus what the start has moved since the note was taken: nothing, while frame and level stay put. Frame and level are still chosen per sample, so audio-rate Position and FM work; a read is only coarse for the rest of a block in which they moved. The second reader's onset is one record further, for the frame to fade to.
- The lengths and starts of the levels are in two message boxes in `ge-osc-wavetable.pd` (into `table $0-len` and `$0-off`, read with `tabread~`) and in `LENGTHS` and `offsets()` in `wavetable.rs`. `wavetable_dsp.rs` fails if they differ.
- **Measured** (`wavetable_dsp.rs`): a saw across the keyboard has every harmonic below 16 kHz within half a percent of what is stored and nothing between them above -88 dB; Position fades between frames per sample; a sine gliding through five levels stays a sine; frame 64 of a full table is as clean as frame 1; the first block is in range; a slot with no wavetable is silent.
- **Banks** are listed in `banks/banks.json` (`id`, `name`, `group`, `frames`), which `src/core/wavetables/banks.ts` imports and `src-tauri/src/banks.rs` includes. An id is saved in patches, so none may change or go: `banks.test.ts` has the list of them. The first groups are made in `banks.rs` from formulas (shape morphs, sync, formants, FM and so on), and anything like chance in them is seeded, since a table is only sent to the Organelle again when its bytes changed. The AKWF groups are Adventure Kid Waveforms, 4,158 single cycles of 600 samples in `src-tauri/wavetables/akwf.bin`, which are CC0 (`AKWF.txt` there): a row's `akwf` is the number of its first cycle. A cycle of any length becomes harmonics by a Fourier transform (`Cycle::from_points`) and is made again at each level's length, which is exact for a periodic wave.
- **A sound file as a wavetable** is cut into cycles of the slot's `cycle` samples; without that, of what the file says in its `clm ` chunk (as Serum, Vital and Surge write it), or by a guess: 16,384 samples are a WaveEdit bank of 64 x 256, up to 4096 samples are one cycle, anything else is in cycles of 2048. More than 64 cycles are thinned evenly, keeping the first and the last.
- **The compiler.** A module with `sample: "wavetable"` reads `ge-wave-<slot>`, the sample modules `ge-sample-<slot>`, and `analyze` says which of the two a used slot needs (`UsedSample.table`, `.wave`): a sound file can be both played and scanned, and then gets both helpers and both files. `CompileResult.samples` says what each file is made from (`sound`, `wavetable` with a path, `bank` with an id), which is `Source` in `samples.rs`; `convert_all` makes it and keeps it, by path and time or by bank id. Where a slot has nothing the module can use there is still a table for Pd (`table ge-wave-<slot> 64`, or a tape of 0 seconds) and a warning: `not-a-wavetable`, `wavetable-as-sample`, `unknown-bank`, or the `empty-sample` there was.
- `ops.place` gives a new Wavetable oscillator a wavetable (one the patch has, or the default in a free slot), and `ops.setWavetable` is the settings pane's quick pick: the oscillator's Wavetable list goes on, after the patch's slots, with every bank there is.
- Not yet measured: what it costs on the Organelle. It is about seventy objects, two table reads and one logarithm per sample per voice.

**Scope.** A Scope module draws the signal at its input on its tile. It is the one module whose point is the editor, and its two settings (Time, Range) say how the picture is drawn: they have receivers in `ge-scope` like any setting, which nothing there uses.

- The route out of Pd is extra output channels. `ge-scope` sends its input to `throw~ ge-scope-<n>`; `host.pd` catches the eight buses into `dac~` 3–10; the engine starts Pd with ten outputs (`PD_OUTPUTS` in `audio.rs`), plays the first two and writes the rest, before volume and fade, into `ScopeStore` (`engine/scope.rs`: atomics, written by the audio callback, read without a lock). The `engine_scope` command gives a window of one slot as a lowest and a highest value for each column of the picture, starting at the last rise through the middle of the signal when asked to trigger. `ScopeView` asks about thirty times a second and triggers up to 100 ms; a longer picture rolls.
- Nothing that reads a scope may take Pd's lock: the audio callback plays silence whenever it cannot get it. That rules out reading Pd arrays from a command.
- `def.tap` marks the module. `analyze` numbers the tapped modules from 1 in document order (`analysis.taps`; 0 beyond `SCOPE_SLOTS`, with the `too-many-scopes` warning), `addModules` passes the number and the voice as second and third creation arguments, and `compile` returns `scopes` (module id → number), which `preview.ts` keeps for the tiles from each load.
- Inside the voices a Scope shows one voice, the one that got the latest note: the voices added up would be a picture of none of them, and `poly` gives each note to the voice that has rested longest, so a fixed voice would show every Nth note. `main.pd` sends that voice's number to `ge-scope-voice` at each key down (only when a voice has a Scope), and `ge-scope` passes its input while the number is its own third argument, `$1` of the voice. Outside the voices the argument is -1 and the input always passes. Until the first note it is voice 0.
- An exported patch keeps its Scopes. No bus is caught on the Organelle, and a `throw~` without a `catch~` is silent and prints nothing.

**Rows layout.** `layout: "rows"` (every module with knobs) lists a module's inputs as rows, two to a grid cell under a half-cell header: the port on the left edge and, where the input has a `param`, that knob beside it. `height` must be `ceil((rows + 1) / 2)`; `registry.test.ts` checks it. `portOffset` in `ui/canvas/geometry.ts` places both the ports and the knobs. A tile one cell wide (Amp, Attenuator, Audio Out) shows the knobs without names. The Attenuator (In times Level, 0 to 1) is a whole module in one cell: its In carries the Level knob, as a Mixer channel does (so its picture, which a narrow tile draws in its first row, is left out), and like those it is silent unpatched rather than resting at 1 (`registry.test.ts` exempts a signal input with a level of its own). Noise and the math and logic operators, with no knobs, keep the plain layout: ports down the edges.

When a module's tile changes shape, older documents can have tiles on top of each other. `ops.settle` pushes them apart, and `actions.openPatch` runs it on every opened patch.

**Modules that grow.** A def with `growsWithInputs` (the Mixer) pairs input *i* with param *i*. Its abstraction and registry def always have all eight, so the compiler and saved documents know nothing about growing. Only the editor does: `visibleDef(doc, module)` in `modules/shape.ts` returns the def cut down to the pairs in use plus one free pair, with the matching tile height, and everything about size or visible ports (`ops.ts` placement and moves, the canvas, the inspector) must use it instead of `getModuleDef`. `ops.connect` calls `makeRoom` when such a tile grows, pushing the modules below it down within the same edit. It uses the rows layout, so the height rule in `shape.ts` has to agree with `portOffset`.

`pd-lib/modules/*.pd` is bundled into the front end with `import.meta.glob(..., "?raw")` in `src/core/pdlib.ts`. `pd-lib/host.pd` is embedded in the Rust binary with `include_str!`.

### Compiler (`src/core/compiler`)

- `analyze.ts` resolves the document against the registry and produces diagnostics (stable `code`s), wires as outlet/inlet indices, normalled connections, pre-cords and knob bindings. Any `error` diagnostic makes `compile` return `ok: false` with no files; warnings still compile.
- **Scope** is where a module's tile lies (see The voice area): inside the area `voice`, in `voice.pd`; outside `global`, in `main.pd`. Nothing else decides it: there was once a rule that whatever a global module fed became global, and a Voice Sum module to mark the way out of the voices; both are gone.
- **Voices are never muted.** Every voice runs its modules all the time and what leaves it is what they make, as on a modular: `emitVoice` connects a crossing's module straight to its `outlet~`. An oscillator with no Amp behind it sounds for ever, in every voice, on C3 (the pitch 60, an octave down) until the voice gets its first note and on its last note after that; so four voices start as four oscillators in unison. Giving a note a beginning and an end is the patch's business: an Amp with an envelope. (An earlier design muted idle voices and kept them alive while an envelope or an effect's tail lasted; it is gone, with the `holdsVoice` and `tail` flags it needed.) The `bare-oscillator`, `voice-effects` and `grains` fixtures are such drones, and `compiled_patches` checks that they sound before any note and after the last.
- **Pre-cords**: an unpatched input with a `precord` is fed from `ge-voice`'s pitch/gate/velocity outlets in the voice area and from `ge-keyboard`'s outside it, unless switched off per instance.
- `emit.ts` writes `main.pd` (`[r notes]`, or a note module, → `[unpack]` → `[poly N 1]` → `[clone voice N]` with a signal inlet for each inward crossing, the modules outside the area, `ge-keyboard` when something there follows the note, a loadbang message box that sends every parameter value) and `voice.pd` (the note `inlet` leftmost, then the `inlet~`s of the inward crossings, `ge-voice`, the modules, an `outlet~` per outward crossing). Box positions mirror the editor grid so exports are readable in Pd.
- **Knob pages.** A patch always has eight (`MAX_PAGES`); there is nothing to add or remove. The document holds them up to the last one with a name or a knob in use (`ops.pageAt` reads one, blank where the document holds none; `renamePage` and `assignKnob` hold more as needed and let go of blank ones at the end, so two documents that say the same are the same). Only the pages with a knob in use are exported: `analysis.pages` is those, in order, and that order is the page number on the Organelle, in `ge-slot-<page>-<knob>`, in the `1/2` on its screen and for Aux. So the third page of the editor can be the second on the device. A page without a name goes by its number in the editor (`defaultPageName`, "Page 3"). `structureKey` covers the exported pages only.
- `knobPages.ts` adds the knob-page section: Aux steps pages, each assigned knob is a `ge-knob` (soft takeover) scaled to its param and echoed to `screenLine1`–`4`, with the page name on `screenLine5`. Screen lines are limited to 21 characters.
- `structure.ts`'s `structureKey(doc)` is the string that decides reload vs. live update. It must cover everything that changes the emitted patch *structure* and exclude param values, positions and the name.
- `src/core/pd/patch.ts` (`PdPatch`) is the only place that writes Pd file syntax; callers pass box text as it appears in Pd and it handles `$` / `,` / `;` escaping and connection indices.

### The CPU estimate (`src/core/cost.ts`)

Every module runs all the time, so a patch costs the sum over its modules of what one copy costs times how many run: once outside the voices, once per voice in them, times a group's size in a unison group. Each voice adds `ge-voice` (`@voice`), and the Organelle's Pd has a base of its own.

- What one copy costs is measured in two steps. `module_cost.rs` runs every module in real Pd on the development computer, sixteen copies fed as the compiler feeds them unpatched (what to measure is `tests/cost/modules.json`, which `cost.test.ts` writes from the registry), and writes `modules/costs.json`, each module's cost in Saws. The CPU probe (`pd-lib/cpu-probe`: banks of Saws, Low-passes and Reverbs switched on by knob 1, the bank picked by knob 2, and the Pd process's `[cputime]` over `[realtime]` on the screen) was sent to an Organelle M with OS 3.2 with the `organelle_send` test, and gave the base (6.5 %) and what a copy adds: Saw 1.39, Low-pass 2.69, Reverb 5.0 %, all in a straight line with the count. The table's relative costs matched the device's within 9 %, so one constant, `ORGANELLE_PER_SAW` (1.35, fitted to the three), turns Saws into percent.
- The top bar shows the estimate as a bar and a figure (`CpuMeter`: the bar amber from `CPU_HIGH` 70 %, red from `CPU_OVER` 85 %, where a tick on its track stands, and full beyond 100 %; the costliest modules in its tooltip), worked out again only when `structureKey` changes. From 85 % `compile` adds the `cpu-load` warning. That line is where the device was heard to fail: Basic Synth with its saw in a unison group played cleanly at 11 copies (estimated 80 %) and crackled now and then at 12 (86 %); Pd needs room for the rest of the Organelle's work.
- After adding a module or changing one's DSP, run `module_cost` again: `cost.test.ts` fails for a module the table lacks. The table is in Saws, so it does not matter that the computer is faster than the Organelle; a new probe on the device would only change the two constants.

### State (`src/state`, zustand)

- `store.ts`: the document, undo/redo history (with coalescing for continuous gestures such as knob drags), selection, file path.
- `preview.ts`: `startPreviewSync()` subscribes to the store. A structural change (different `structureKey`) recompiles and reloads the patch after a short debounce; a value-only change sends each changed param to its receiver and nudges the matching `ge-slot-<page>-<knob>` so the on-device knob state and screen follow. It also keeps what the patch sends back (screen lines, Pd console) in the `usePreview` store; the components only draw it. Pd's printed lines (`console`, from the first load on) are read by `state/console.ts`: libpd marks an error `error: ` and a post `verbose(n): ` (0 and 1 are errors, as in "... couldn't create"; above 2 they are left out, as Pd's own window does), and a line already there is not added again, since a reloaded patch prints its errors again. A new error opens the Problems pane.
- `actions.ts`: opening and saving presets, Export and Send.
- `presets.ts`: the list of the presets the user has saved, read again when the Presets pane opens, after a save or a delete, and when the window comes back to the front.
- `organelle.ts`: the Organelle's network address (kept in `localStorage`) and how the current or last send went, which the Organelle pane shows.
- `ui.ts`: transient canvas state (view, cable drag, palette placement), the knob page on show and the Organelle knob being assigned.
- `assign.ts`: assigning Organelle knobs by clicking (below).
- `clipboard.ts`: the modules last copied, and where a paste goes. The clipboard is the editor's own (a variable, not the computer's clipboard) and outlasts the patch, so modules can be taken from one preset to another. A paste goes under the pointer (`gridPointer` in `ui.ts`, which `GridCanvas` keeps and which is not in the store, since it changes with every move) or in the middle of the view, and the view moves, as little as it takes, to show what was pasted (`viewShowing` in `canvas/geometry.ts`).

Hot reload does not survive an edit to these store modules: the UI switches to a new store instance while the sync started by `App` keeps feeding the old one, so the preview looks dead (blank screen, no reloads) until the window is reloaded or `tauri dev` restarted.

### UI (`src/ui`)

- Components change the document only through `useEditor.getState().apply((doc) => ops.something(doc, …), coalesceKey?)`. Continuous gestures pass a key (`param:<module>:<param>`, `patch-name`, `page-name:<index>`) so the whole gesture is one undo step.
- **Side panes** open at either side of the window, from the top bar down to the dock, from tabs at that end of the top bar (`ui/shell/SidePanes.tsx`); the module browser and the grid move over. `SIDE_PANES` lists them: an id (`SidePaneId` in `state/ui.ts`, with its side in `PANE_SIDE`), the tab's name, and the component that fills the pane. `useUi.sidePanes` has the open one of each side (the editor starts with Presets open); a click on its tab closes it, and `showSidePane` opens one from code. On the left, before the patch's name, is Presets (`shell/PresetsPane.tsx`, below). On the right are Samples; Organelle (`shell/OrganellePane.tsx`), which holds Send over Wi-Fi with its address and outcome, and Export; and Problems (`shell/ProblemsPane.tsx`), what Pd printed, whose tab is there only while there is something (a pane's `useShown`); its Dismiss button clears it and closes the pane (`dismissConsole`). `sendToOrganelle` opens the Organelle pane, so the ⇧⌘E shortcut shows what it is doing. A new pane is one more entry in the list. Besides the tabs the top bar has the patch's name, in the middle of the window and to type over (`.heading-field` in `App.css`, the style a module's name and the patch's name in the settings pane share: a heading that shows as a field when pointed at), and, only when something keeps the preview from playing the patch, a status. There are no Undo and Redo buttons: `useShortcuts` in `App.tsx` handles ⌘Z and ⇧⌘Z, and copy, cut, paste, duplicate, delete and ⌘G the same way. In a text field those keys are the field's own (`ui/textField.ts`), and ⌘C with text selected (the settings pane's texts can be) copies the text.
- **The menu bar** of the desktop app (`bridge/menu.ts`, installed once at start; nothing in a plain browser) has File (New Patch, Open…, Save, Export…, Send to Organelle) and Edit (Undo, Redo, Cut, Copy, Paste, Duplicate, Delete, Select All, Put in Unison Group, Ungroup). Its items and the keys run the same commands (`state/commands.ts`, `runCommand`); since an item has the key's shortcut, one press may reach both, and the second from the other source within 250 ms is dropped (a key held down repeats). Undo, Redo and Select All are the editor's, acting on the text instead when a text field has the focus (`document.execCommand`). Cut, Copy and Paste are the system's own, because a page may not paste into a field by itself; on the patch the page answers the `cut`, `copy` and `paste` events they bring, which a key the page handled never does. Duplicate, Delete, Put in Unison Group and Ungroup are greyed out when they do not apply. None of this can be tried in a plain browser: check it in `tauri dev`.
- **Presets** are how patches are opened and saved: there are no file dialogs for them. They are the `.gridelle` files in the Gridelle folder of the user's Documents, and the pane lists exactly those, in one list. The editor keeps no presets anywhere else: the ones it comes with (`EXAMPLE_PRESETS` in `core/presets.ts`, which are New patch and a few of the fixtures that play no sound file) are written into that folder when the editor starts (`startPresets`), each of them once ever. A hidden file there, `.gridelle-examples`, has the names written so far, so one the user deletes stays deleted and one a later version adds is written then (`presets::seed`). A preset the user already has under such a name is not written over, unless its document version is older than the example's: this editor cannot open it, so the example takes its place.
  - A click opens a preset. Save writes the patch as `<name>.gridelle`, where the name is the patch's own less what a file name cannot hold (`presetFileName`, the same rule as `is_preset_name` in `src-tauri/src/presets.rs`). It writes over the patch's own file without asking, and asks before replacing another preset of that name; a renamed patch is therefore saved as a new preset beside the old one, which is also how one is copied. Each row has a delete button.
  - "New patch" (`NEW_PATCH_NAME`) is a file like the others and the base of new patches: opening it, from the list or with ⌘N, gives a copy that is saved nowhere, so saving that under the same name asks before it replaces the base. That question is how a user makes a base of their own. Without the file, ⌘N gives the `newPatch` document.
  - Under the list are the patch's name as a field (the same `doc.name` as in the settings pane, one undo step per run of typing, Enter saves) and the Save button. ⌘S saves and ⌘O opens the pane.
- The window is the top bar, the module browser over the grid (with a side pane to their right when one is open), and the dock (`shell/Dock.tsx`): the virtual Organelle (its keys hidden until the keyboard button beside its knobs shows them; the computer's keys play either way), the Knob pages panel and the settings pane (`inspector/Inspector.tsx`). The settings pane shows what a selected module does (`MODULE_DOCS` in `core/modules/docs.ts`, one short sentence by module type, saying nothing the grid shows; `docs.test.ts` fails for a module without one, for one longer than a line, and for a text that names a port or setting the module does not have) and what it has besides the knobs on its tile, which is its choices and its pre-cord switches, or the patch's name, voices and problems when no module is selected. A numeric setting is only on the tile.
- A click on an input that has a pre-cord, with no cable in it, switches the pre-cord over (`ops.togglePrecord`); a press that moves is a cable drag as on any port (`onPortPointerDown` in `GridCanvas`). The switch in the settings pane does the same.
- A tile drag keeps the modules in their containers unless Shift is down (at the press, during the drag, or pressed without moving the pointer); Shift and a click without a drag still adds the module to the selection or takes it out. The canvas shows what the move would do (`ops.moveModules` on the drag), tiles pushed and containers grown, before the drop.
- The voice area is drawn by `canvas/VoiceArea.tsx` under the tiles (a click on its header with no drag clears the selection, which shows the voice settings): one dark translucent panel with rounded corners, red while a drag would be refused by `moveArea` or `resizeArea`. Its header row is drawn darkest, and the left column below it, the container's shelf (`.container-shelf`), between that and the rest; a unison group is drawn the same way (`Frame` in `VoiceArea.tsx`). No line of a container runs along a tile's: the panel is drawn `CONTAINER_PAD` (8 px) in from its cells, and the header's bottom and the shelf's right side stop that far short of its inside, the shelf's ports keeping their place from its edge (`shelfPortPoint`). The border's cells are what takes hold: the header moves the area with its tiles; the sides, the bottom and the corner resize it, and while they are dragged the tiles a resize would push are drawn where they would go. The inside lets presses through to the grid, so a marquee starts there as anywhere.
- `canvas/geometry.ts` is the single source of tile and port positions. Tiles and ports are placed from it and cables are drawn to the same computed points, not measured from the DOM. Dropping a cable finds its target through the ports' `data-port-*` attributes (`portUnder`).
- `palette/Palette.tsx` is the module browser, a strip above the grid: the categories that have modules on the left, the chosen category's modules as a row of cards on the right. A card is pressed and dragged onto the grid (`useUi.placing`; `GridCanvas` draws the ghost and adds the module) or clicked to land near the centre. Each card's picture is a path in `palette/glyphs.ts`, keyed by module type; `glyphs.test.ts` fails for a module without one. The same picture is on the module's tile (`Glyph` in `ModuleTile.tsx`): left of the name, or on a tile one cell wide, which has no room there, in the middle of the tile below the name.
- While a module from the browser is held over a port, `GridCanvas` shows the `planPortDrop` plan: the ghost at the landing cell, the planned cables dashed (the cables they replace hidden), and the tiles a push would move already slid aside. Sliding a tile takes its port out from under the pointer, so the aimed-at port is held for as long as the pointer stays where the port was found.
- The Knob pages panel (`pages/KnobPages.tsx`) starts with one strip for going from page to page: previous, the page's name as a field (its number as the placeholder), a list of all eight pages (a native `select` under a caret button, which says which pages are empty), next. `useUi.knobPage` is the page on show, 0 to 7.
- A setting goes on an Organelle knob in two clicks: an unassigned knob in the Knob pages panel, which arms it (`useUi.assigning`, `state/assign.ts`), then a knob on a tile. `ParamKnob` takes that press in the capture phase, so the dial does not turn, and `assignToArmed` arms the page's next empty knob or ends the mode. Any other press ends it (`useAssignCancel` in `App.tsx`), as do Escape and the armed knob becoming taken or gone (an effect in `KnobPages`). While armed, cables ignore the pointer, since one may lie over a knob.
- Styling is plain CSS per component. Colour comes from `category-<Category>` and `hint-<SignalHint>` classes that set `--category` / `--hint` in `src/App.css`, so a new category or hint needs an entry there.
- A knob page has a colour by its position (`page-color-<index>` in `src/App.css`, setting `--page` and `--page-ink`): the badge on a tile knob, and in the Knob pages panel the edge of the page's name and the knob numbers. Clicking a badge shows its page in the panel. The eight colours are a colour-blind-safe set (Okabe-Ito) in a deliberate order; the comment there has the measured separations, and `pageColors.test.ts` checks contrast. Change a colour only with a simulation at hand: colour is backed up by the knob number, the tooltip and a ring on the badges of the page the panel shows (`useUi.knobPage`), because the sixth colour is close to the fourth for deuteranopes.

### Bridge and Rust back end

The UI reaches Pd only through the `PreviewEngine` interface in `src/bridge/engine.ts` (Tauri commands `engine_*` plus the `pd-event` event); in a plain browser it is replaced by a silent stub. File dialogs and disk access are in `src/bridge/files.ts`. The Tauri commands are in `src-tauri/src/lib.rs`. The capability file grants only `core`, `opener` and `dialog`: reading, saving and exporting go through the custom commands there (`read_text_file`, the `presets_*` and `preset_*` commands, `export_patch`), not a Tauri fs plugin. The preset commands work only in the presets folder (`presets.rs`: one plain file name, written through a temporary file, deleted only if it is a preset directly inside that folder); nothing writes a file at a path the front end chooses.

- `build.rs` compiles libpd's C sources straight from the `vendor/libpd` submodule with `cc`: single precision, and of the `extra` externals only those a module wraps (`EXTRA_SOURCES`, so far `bob~`), so that nothing else can work in the preview by accident.
- `engine/pd.rs` is the safe wrapper. libpd is global state, so there is one `Pd` behind a mutex and every libpd call holds it. `Pd::init()` returns the event receiver only on its first call in a process, which is why each file in `src-tauri/tests` has a single `#[test]`.
- `engine/audio.rs` runs Pd inside the cpal callback (`try_lock`, never blocking), with ten output channels of which the device gets two (see Scope), applies queued messages from a lock-free ring buffer at the start of each callback, and swaps patches by fading out, taking the lock, closing the old patch and opening the new one from a per-revision temp directory. It also keeps the highest level of each input and output channel (the output after the volume, as heard) in atomics, which the `engine_levels` command reads and clears.
- **The level meters.** The virtual Organelle's screen has the device's top row above its five lines (`Meters` in `VirtualOrganelle.tsx`): I and O, each two rows of eleven segments, left over right, drawn pixel for pixel as Organelle OS 3.2 draws the Organelle M's (`OledScreen::drawInfoBar`, without its battery and Wi-Fi signs). `ui/organelle/meters.ts` turns levels into segments as the device's host patch does (`mother.pd`, Critter & Guitari's own `pvu~ 100`, which gives the peak itself, not dB): every 100 ms the peak since the last reading, or the held one falling over 300 ms; input `sqrt(peak) * 14 - 2`, output `sqrt(peak) * 12`, whole numbers from 0 to 11. The input is silent while the patch has no Audio In, since the input is open only then.
- The audio input is opened only while the loaded patch has `ge-audio-in.pd` among its files (so the microphone is not live otherwise), at the output's sample rate. Its callback writes into a ring buffer that the output callback reads a Pd block at a time, behind a cushion of about 23 ms because the two callbacks do not run in step; `host.pd` passes Pd's `adc~` on as `inL` / `inR`. When it cannot be opened, `Engine::load` returns the reason and the patch plays with silence there. `Pd::process` has silence at the input; `process_with_input` is what the callback and the tests use. The bundled app needs `NSMicrophoneUsageDescription` (`src-tauri/Info.plist`).

### The Organelle contract

Exported patches must run on the device's stock Pd (0.49 on OS 3.x and 4.x: its core objects and what its own `extra` folder holds, no other externals) under the Organelle's own host patch:

- Input from the host: `notes` (pitch velocity), `knob1`–`knob4` (0–1), `aux`, and its audio input as the signals `inL` / `inR` (read with `r~`; seen in the `mother.pd` of a device with OS 3.2).
- Output to the host: `throw~ outL` / `throw~ outR`, `screenLine1`–`screenLine5`, `led`.
- Exports never contain `dac~` or `adc~`. In the preview and in the Rust tests `pd-lib/host.pd` stands in for the host (catch → clip → `dac~`, plus the Scope buses on outputs 3–10), and `src/ui/organelle/VirtualOrganelle.tsx` sends exactly the messages above and shows the screen lines (not the LED, which only says the knob page).
- `pd-lib/spike` is a hand-written patch for checking a real device, not compiler output. So is `pd-lib/cpu-probe` (generated once, not by the compiler), which measures CPU on the device: see The CPU estimate.

### Sending over Wi-Fi (`src-tauri/src/organelle.rs`)

"Send to Organelle" runs the same compile as Export and hands the files to the `organelle_send` command, which talks to the web file manager the Organelle runs while it is on Wi-Fi. There is no documentation for that server; the facts below come from the Organelle_OS source (tags v3.2, v4.4, v5.1) and from a device running OS 3.2.

| | OS 3.x–4.x ("classic") | OS 5 |
|---|---|---|
| Server | CherryPy, port 80, under `/files` | Flask, port 8080, no prefix |
| List / make folder / delete | `GET /files/fmdata?operation=get_node\|create_node\|delete_node` | same; the JSON answer is encoded twice |
| Upload | `POST /files/upload`, multipart `dst` + `files[]` | `POST /upload` |
| Read back | `GET /files/download?fpath=&cb=` (both required) | `GET /download?fpath=` |
| Refresh the patch menu | `GET /files/resync` | automatic after an upload |
| Start a patch | OSC `/loadPatch <folder name>` to UDP 4001 | `POST /reload_patch`, form `path=<folder>` |

- Uploading or creating never overwrites: a taken name becomes `main 2.pd`. A file is therefore deleted before it is uploaded.
- Every operation answers `{"ok":"ok"}` even when it failed, so each file is downloaded and compared after sending.
- The device plays from `/usbdrive/Patches` when that exists, otherwise `/sdcard/Patches`. It records the running patch as a folder name under `/tmp/curpatchname`, which is how a classic start is confirmed.
- A folder counts as Gridelle's own, and is replaced without asking, when it contains `ge-voice.pd`.
- A patch's sound files (`ge-sample-<letter>.wav`, and the wavetables `ge-wave-<letter>.wav`) are uploaded before its patch files, and one the device already has, byte for byte, is not sent again.
- After a send, the `ge-*.pd`, `ge-sample-*.wav` and `ge-wave-*.wav` files in the folder that the patch no longer has are deleted (modules and samples removed since the last send). Nothing else in the folder is touched: it may hold the user's own files.

`src-tauri/tests/organelle_send.rs` holds a fake device that reproduces both servers and these quirks. The OS 5 path has only ever run against that fake.
